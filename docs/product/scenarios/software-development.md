# 场景一：软件开发场景拆解与产品思考

软件开发是 Perga 现阶段首个重点打磨的领域。但“软件开发”并不是一个均质场景——修一个紧急 Bug、做一个新功能、写一份架构设计、常年维护一个模块、值守线上稳定性、以及跨周推一场大重构，它们的工作节奏、核心瓶颈与人的介入方式完全不同。

本文刻意**不从既有系统模块出发“画靶子套场景”**，也不讨论底层实现，而是回到真实软件工程现场：先逐一还原 6 类典型开发工作的本来面目与理想 User Flow，再从中归纳**真共性**与**真差异**，最后反推出产品设计必须正面回答的核心命题。

---

## 一、六类真实开发场景的结构化全景

| 子场景 | 生命周期 | 核心起点 | 核心瓶颈 | 人类最高杠杆的介入点 | 什么时候算完成 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 修 Bug（排障）** | 短平快（数十分钟–数小时） | 报错堆栈 / 现象 / 失败链接 | 复现与收窄假设空间，防治标不治本 | 确认是否真根因（无法复现时补线索） | 复现用例先红后绿 + 最小修复合入 |
| **2. 开发功能（Feature）** | 单次交付（数小时–数天） | 需求 / Issue | 边界歧义、过程看不到真实效果、大 Diff 审不动 | 开工前定清非目标 + 验运行效果 + 审核心 Diff | 需求验收通过、PR 合入并归档 |
| **3. 技术设计 / 预研（RFC）** | 探索收敛（数小时–数天） | 开放问题 / 架构提案 | 脱离代码纸上谈兵、方案盲区、高密度共创沟通 | 直接在方案段落上划词批注、逐条拍板关键取舍 | 设计定稿归档，并可拆出后续开发任务 |
| **4. 模块维护与开源运营** | **常青无终点（数周–数月）** | 新 Issue / 外部 PR / 依赖通告 / CI 抖动 | 高频琐碎打断心流、80% 重复分诊与初审劳动 | 平时免打扰；按节奏处理极干净的待批队列 | 永不关闭，持续维持模块健康与响应速度 |
| **5. 长期运维与性能优化** | **常青双节奏（应急 + 跨周实验）** | 线上告警 / 性能与稳定性指标目标 | 应急态需要秒级归因止血；优化态跨周易忘旧实验 | 告警时拍板“止血 vs 根治”；定期审视指标演进 | 应急快速恢复；优化指标达标并持续守住 |
| **6. 长期架构师与大重构** | **跨周多阶段战役（数周）** | 架构腐化体检与重构目标 | 巨型分支合不回去、重构偷偷改坏行为、边治边漏 | 批准切片顺序 + 遇历史耦合拍板 + 核对债务下降 | 债务指标达标、所有切片安全合入并固化门禁 |

## 二、六类场景的本来面目与理想 User Flow

### 1. 修一个 Bug（排障与回归）

- **真实世界的难点**：起点永远是凌乱的线索（一段日志、模糊反馈、偶发失败的 CI）。80% 的时间不在写修复代码，而在**提出假设 → 查日志/看近期变更/搭复现 → 证伪假设 → 缩小包围圈**。最容易搞砸的是没复现就加防御性 `if` 治标不治本，或偶发 Bug 跑通一次就以为修好。
- **理想 User Flow**：
  1. 人把报错堆栈、失败链接或现象直接甩给系统，无需先写长文档；
  2. 系统**严禁一上来直接猜着改业务代码**，而是并行排查多条假设（查近期提交、顺调用链查源码、搭最小复现环境）；
  3. 像**侦探板**一样把“已证伪的假设 / 已坐实的证据链 / 稳定复现的红灯用例”摊在眼前；若无法复现，诚实停下并列出已排除项与缺失日志请人补线索；
  4. 人 30 秒确认“找对真根因了”后放行修复；
  5. 必须亲眼看到**刚才那个红灯复现用例转绿 + 受影响测试全绿**，并顺手扫一遍全仓有没有同款漏洞，最后以极紧凑的故障卡（根因一句 + 最小修复 Diff + 红转绿证据）收口合入。

### 2. 开发一个功能（Feature 交付）

- **真实世界的难点**：返工主要来自三处——开工前隐含假设没对齐（兼容旧数据、异常态、非目标）；实现中看不到真实交互效果（尤其前端与端到端流程）；写完面对几百上千行按字母序排的原始 Diff，人没精力逐行查又不敢闭眼合。
- **理想 User Flow**：
  1. **轻重自适应**：小修小补一句话发出后直奔实现与验证，几分钟收口；中大型功能才进入完整闭环；
  2. **开工前消歧**：系统先只读摸清仓库约定与关联模块，立出极简的《目标 / 非目标 / 验收标准》，只针对真正影响方向的歧义问 1–2 个选择题；人花几分钟定好边界后即可放心离手；
  3. **真实可感的过程与验证**：后台静默推进实现、独立挑刺审查与全量验证；界面或交互类改动提供可直观查看的真实运行结果/截图；人随时可钻进具体执行现场发一句纠偏指令；
  4. **导览式收口（Guided Diff）**：收口不甩一坨字母序 raw diff，而是把**核心逻辑与高风险边界改动**（数据变更、公开契约、状态流转、权限检查）置顶、把机械修改与测试补丁折叠在后，点任意审查意见直达对应修复 Diff，让人花 1 分钟看最值钱的核心代码与客观验证绿灯后从容合并。

### 3. 做一个技术设计 / 架构预研（Design & RFC）

- **真实世界的难点**：产出物**根本不是合并代码**，而是一份高成本、难逆转的技术决策。真实写设计时，人不是被动“听汇报”，而是需要**像在协作文档里一样直接划中某一段落批注追问**；同时纯文字架构极易脱离现网代码真实耦合，而很多方案争论必须靠 20 分钟小原型实测数据（Spike/POC）才能拍板。
- **理想 User Flow**：
  1. 人抛出开放命题（如存储演进、模块拆界、并发恢复模型）；
  2. 系统先对现网代码做实证摸底，拉出 **2–3 套备选方案的硬核对比**（拒绝只给一个“自以为最优”的单一答案），并专门引入**红队对抗视角**逐项挑并发、迁移、兼容与回滚死角；
  3. 遇到拿不准的性能或兼容性假设，顺手在隔离区跑一个一次性小实验，把实测数字嵌进方案对比，实验代码随手丢弃不污染仓库；
  4. 人在方案文档里**直接划选段落写行内批注、质疑或修改**，聚焦“待拍板分歧清单”逐条收敛；
  5. 方案定稿归档后，可直接拆出 1–N 条后续“功能开发”任务，设计结论自动成为下游开发的锁定约束。

### 4. 长期维护一个模块 / 开源仓库（Module Maintainer）

- **真实世界的难点**：没有“做完就关”的终点，面对的是**持续不断涌入的外部水流**——新 Issue、外部 PR、用户提问、偶发 CI 失败、依赖安全公告、文档过时。高频琐碎疯狂打断心流，80% 是重复分诊与基础初审，真正需要维护者大脑的只有 20% 的方向与质量判断。
- **理想 User Flow**：
  1. 维护任务常驻运行，持续汇聚模块的外部水流与健康状态（未分诊 Issue、待审外部 PR、CI 稳定度、依赖安全通告）；
  2. 系统像 7×24 值班的副维护者，自动判重并帮新 Issue 补复现、给外部 PR 做首轮深度 Review、自动验证小版本依赖升级与明确 Flaky 修复；
  3. **常态绝对安静**，不每来一条消息就弹窗轰炸；
  4. 维护者按自己的节奏打开一份极干净的**待批队列**：哪些低风险小修已验证完毕可直接一键合、哪些外部 PR 或新需求需要拍板方向。

### 5. 长期运维 / 稳定性与性能持续优化（Ops & SRE）

- **真实世界的难点**：面对活生生的运行系统与持续波动的指标（延迟、内存、错误率、成本、CI 时长），存在**应急态**与**优化态**两种截然不同的节奏：故障时分秒必争要先止血，事后再根治；性能优化则是跨周反复试错，最容易忘掉三天前失败过什么方向或靠作弊刷指标。
- **理想 User Flow**：
  1. **平时静默盯盘**：持续采集真实运行指标与关键日志，一切在安全水位内时零打扰；
  2. **应急态（告警触发）**：第一时间自动关联近期变更与错误日志完成只读归因，立刻置顶弹出清晰选择——**「先止血回滚/降级」vs「直接根治修复」**，附带各自影响面，让人秒做决策，事后自动沉淀事故复盘；
  3. **优化态（跨周指标攻坚）**：锁定清晰目标指标，自主进入“提假设与局部预期 → 隔离实验 → 对比真实指标曲线 → 达标保留 / 退化显式回滚并归因”的持续循环，完整保留每次成功与失败实验的账本。

### 6. 长期架构师：架构整理与跨周大重构（Continuous Architect）

- **真实世界的难点**：代码库在几十个日常功能 PR 堆叠下悄悄腐化（巨石文件、循环依赖、边界渗漏、重复实现）。大重构最致命的死法是**停下业务攒一个几百文件的巨型分支，最后冲突到合不进去、或者重构中途偷偷改坏了业务语义**；好不容易改完，两周后新 PR 又把脏依赖引回来。
- **理想 User Flow**：
  1. **先体检立总账**：对代码库做结构扫描，量化当前架构债务（超大文件数、违规跨层依赖、重复实现、核心契约覆盖率）与目标水位；
  2. **拆成可独立安全合入的渐进切片（P0 → P1 → P2 ...）**：硬约束是**每一片都足够小、能独立验证、独立合入主干、不阻塞日常业务开发**；
  3. **每片严守行为等价性**：逐片推进并持续跟进主干变动，用等价性测试与独立审查确保“只改结构、不夹带未授权的行为变更”；每合入一片，架构债务总账真实刷新下降，防止“忙活两周只在倒腾风格”；
  4. **把治好的边界固化成永久守门员**：重构拆清的模块边界同步沉淀为自动化静态/架构检查，防止未来新代码再次腐化；战役跨越数周，人随时中断去做急活，一周后回来十秒就能接上进度。

## 三、跨场景共通的三种逆风 User Flow

无论上面哪类开发工作，只要涉及代码修改与多视角协作，都会高频撞上三种真实的逆风局：

1. **审查反复打回或两路意见冲突（自动熔断与快速裁决）**：修复一轮引入新回归、或两个审查视角互相矛盾时，绝不无限空转烧额度——到达阈值自动暂停并置顶冒泡，直接浓缩呈现“核心分歧 + 双方论据 + 2–3 个裁决选项”，人 15 秒定调后恢复推进。
2. **临门一脚上游主干变了（自动 Rebase 与分级重验）**：多任务并行时别的 PR 先合入主干——若为纯机械变基且全量验证全绿，静默刷新状态不打扰人；若出现冲突或行为语义变化，精准冒泡高亮影响面并在解决后触发增量复审。
3. **干到一半假设推翻或需求大改（原地干净转向）**：不必手动清分支重开窗口——人在边栏下达转向指令后，干净中止旧执行、安全回退脏改动、原地刷新目标共识（旧尝试折叠进历史），轻装重跑。

## 四、从 6 个场景里长出来的「真共性」与「真差异」

把 6 个真实场景并排摆开，不预设任何现有软件形态，能清晰看到两类结论：

### A. 5 条真共性（真正应该沉成产品底座的能力）

1. **核心状态必须外化为结构化“活现场”，绝不能埋在聊天流里**：不管是排障侦探板、设计决策表、功能进度证据、模块健康队列，还是重构债务地图，都需要持久化且随进展自动演进。
2. **单一视角永远不可靠，必须内置多视角与对抗校验**：并行验多假设（Bug）、独立审查（Feature）、红队挑刺（Design）、等价性核查（Refactor），对抗是所有严肃工程的刚需。
3. **一切判断必须接在真实环境与客观证据上**：真实复现红绿灯、真实测试与运行预览、一次性 POC 压测数字、真实监控与依赖图——脱离真实执行现场的协作都是纸上谈兵。
4. **必须承接跨时间周期的异步节奏与低噪唤醒**：平时绝对安静，只在需要人类拍板、裁决分歧或处理告警时冒泡。
5. **人类随时可以打破黑盒、精准介入**：随时看清现场、随时拉回跑偏思路、随时推翻重来。

### B. 4 处真差异（硬用同一套页面去套就会出问题）

1. **「只读审批」vs.「高密度行内批注」**：运维告警、阶段进度、客观验证结果必须只读防篡改；但在**技术设计（RFC）**与**核心 Diff 审阅**中，人强烈需要像协作文档一样**直接划选段落或代码行留批注**，而不是在边栏聊天框里隔空描述“上面第三段第二句不对”。
2. **主屏的信息形态根本不同**：排障需要**假设树与证据链**；功能开发需要**边界、进度与导览式 Diff / 运行预览**；设计需要**多方案对比、红队攻防与决策清单**；运维/维护需要**外部事件队列与健康指标**；大重构需要**债务总账与跨多 PR 切片路线图**。
3. **「单次交付」vs.「常青母体派生多次交付」**：修 Bug 与小功能基本是“1 个任务 = 1 个 PR”；但**模块维护**与**跨周大重构**是“1 个长期常驻母体，持续派生并追踪 5–20 个独立合入的小 PR”。
4. **“验证通过”的定义完全不同**：Bug 是先红后绿；Feature 是符合需求与真实运行效果；Design 是边界漏洞排查与 POC 实测；Refactor 是结构指标下降且外部行为严格等价；Ops 是指标回归稳定且可回滚止血。

## 五、反推产品设计必须正面回答的 3 个核心命题

脱离“先画靶子再套场景”后，上述真差异直接暴露出三个产品设计上必须认真回答的问题：

1. **「长期母体 → 派生多个短期交付」的层级模型怎么设计？**
   只把“单任务 = 单 PR”做顺，承接不了**模块长期维护**和**跨周大重构**。产品需要一种轻盈、不官僚的方式，让一条常青维护任务或重构战役能够持续派生、跟踪并汇总多个独立合入的短期交付，而不是把 10 个 PR 硬塞进同一个工作区或退回手工管理。
2. **「不可篡改的只读事实层」与「高密度行内批注层」如何并存？**
   保持指标总账、进度拓扑和验证证据的只读权威是对的；但面向**设计方案正文**与**关键代码 Diff**，需要探索轻量的“划选批注 → 直接发给负责人修订”交互，既不滑向重型双向富文本编辑器，又补齐深度共创与代码审阅的效率短板。
3. **按三种典型形态作为产品设计标尺，逐个吃透而不硬搞一刀切**：
   - **短/中收敛型**（修 Bug + 功能开发）：追求零配置起手、先复现/先定边界、导览式看核心 Diff；
   - **高密度共创型**（技术设计 / RFC）：追求代码实证、红队对抗、一次性 POC 与行内批注收敛；
   - **常青/多阶段型**（模块维护 / 长期运维 / 跨周大重构）：追求静音守望、健康/债务总账、以及从母体持续派生可安全合入的切片。

只要底层产品抽象能自然、不拧巴地同时撑住这三种完全不同的形态，软件开发这个主战场才算真正立稳。
