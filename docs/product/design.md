# 产品设计与痛点优先级

[愿景与根本矛盾](vision.md)定义的是长期北极星，但具体做产品与实现时必须**反过来想小、想具体**：不试图一次性造一个大而全的“AI 组织操作系统”，而是沿着通往愿景的路，**把当下最卡脖子的几个具体小痛点按优先级排出来，一个一个用最克制的手段解透**。

现阶段的设计重心全部收敛在一个最小工作单位里——**先把单个跨天/跨周任务（`Track`）跑顺手**。下面按优先级列出正在解决与刻意暂缓的 6 个具体问题，以及每个解法背后刻意放弃的替代方案。

## 痛点优先级总览

| 优先级 | 具体痛点 | 当前最小解法 | 当前状态 |
| :--- | :--- | :--- | :--- |
| **P0** | 1. 流式聊天对话的长期状态漂移 | 对话退到边栏，主屏用只读活报告 + 强校验小账本 + 内核写实进度锁住状态；上下文满时锚定报告换页 | 已打通主干 |
| **P0** | 2. 异构模型的组织、制衡与黑盒失控 | 单 Track 内单 Lead 统一调度 Claude / Codex / ACP；审执物理分离 + 强制异构模型审查 + 门禁拦截；人机共享实时流与 Steer | 已打通主干 |
| **P1** | 3. 多 Agent 的编排、傻等与唤醒 | 轻量声明式 `flow.json` 统一并发依赖、`cron`/`at` 定时与 0-Token 外部 `watch` 探针；异常决策交回唤醒后的 Lead | 主干已落地 |
| **P1** | 4. 并行工作区的环境踩踏与现场易碎 | 一任务一隔离区（Worktree / `jj` / OverlayFS 预热缓存 / SSH），独立终端守护进程重启不断连 | 已打通主干 |
| **P2** | 5. 重复规矩固化 vs. 冷启动过重 | 默认零模板一句话开干，规律浮现后按需挂载或由 AI 生成极轻协议（27–40 行、优先原生内置视图，随时可拆） | 主干已收口 |
| **P3** | 6. 多任务扩张后的跨 Track 协同与全局过载 | 现阶段刻意克制，仅保留 Area 分组、跨 Track 异步 Mail 与 Today 每日变更流；重型全局能力排在后续 | 刻意暂缓 |

## P0-1：流式聊天对话的长期状态漂移

- **痛点**：一个任务只要跑过两天、聊过几十轮，需求边界、已确认结论和当前进度全淹没在聊天流里；触发上下文压缩或切换会话后，AI 很容易忘掉早期约束、越改越飘；人回头接手也要翻几百行记录才能拼出“现在到底进行到哪了”。
- **具体解法**：
  - **两栏分工**：把聊天留在边栏，主屏固定是一份**只读的活报告（Report）**——给人十秒扫清现状（排版原则见 [模板 Taste 与信息设计原则](../design/template-taste.md)）；
  - **账本与真账分开记**：容易飘的业务状态（如 KR 指标、估值锚点、事件预期）放进强校验的结构化小账本（`Track.Data`），AI 只能按严格格式增量更新；而任务状态、实际执行模型、门禁退出码与更新时间全部由内核直接填入，AI 改不了；
  - **无损续命**：会话上下文逼近上限时，优先触发底层原生压缩，不支持则以最新 Report 为锚点做 Epoch 换页，保证状态不随对话流腐烂。
- **刻意不选什么**：**刻意不做 Notion 式人机双向协同富文本编辑器**。一旦允许人在主屏直接编辑块内容，就会立刻陷入双向合并冲突与表单噪音，破坏“AI 维护出版物 + 内核单向投影事实 + 人通过边栏对话下意图”的清晰边界。

## P0-2：异构模型的组织、制衡与黑盒失控

- **痛点**：不同厂商的模型能力曲线明显分化（例如有的适合架构分析与挑刺，有的适合大批量代码实现），且同一个会话既当运动员又当裁判极易偷懒走捷径；现实里开发者只能手工开多个 CLI 窗口来回复制上下文。同时，后台子任务一旦跑成黑盒，写偏了也无法及时拉回。
- **具体解法**：
  - **同一任务内跨厂混编**：由一个主理（`Lead`）在同一工作区与活报告下，按需拉起 Claude Code、Codex、ACP 等不同厂商的 `Worker`，不再手工搬运上下文；
  - **硬制衡防偷懒**：执行任务的契约 Worker 物理上无权调用 `flow_commit` 修改调度计划或越权调用治理工具，仅通过 `task_done(outcome, summary)` / `task_fail` 交卷；通过路由规则（`routing.enforce`）强制把审查/复核派给另一家只读模型，写任务强制跑验证门禁（Gate），后续推进与高风险决策由 Lead 或人工确认把关；
  - **打破黑盒**：人与 Lead 看到的是同一份 Worker 实时流；人发现跑偏时直接发一句 `Steer` 纠偏，或者随时中断、换模型接着跑。
- **刻意不选什么**：**刻意不做多 Agent 自由群聊（去中心化 Swarm）**。多个平等 Agent 在同一频道自由讨论，通信复杂度呈 $O(N^2)$ 失控且无人对最终验收负责；坚持“单一 Lead 统筹 + 隔离 Worker 交卷”的最小权责结构。

## P1-3：多 Agent 的编排、傻等与唤醒

- **痛点**：长期任务有大量时间花在并发汇合与外部等待上——等并行两路 Review 都结束、等 GitHub PR CI 跑完、等明早 9 点采一次线上指标。靠人盯着催没法扩展；靠 LLM 循环轮询既烧 Token 又脆弱；写成静态流程一遇意外又僵死。
- **具体解法**：
  - 用一份极轻的声明式 `flow.json`（详见 [Unified Track Flow 架构](../design/unified-track-flow-architecture.md)）只管三件具体的事：**并发依赖（`after`）、周期/定时触发（`cron` / `at`）、以及零 Token 外部探针（`watch` 盯 PR Checks 或 shell 命令输出）**；
  - 外部状态没变化时完全不调用模型、不花 Token；条件满足或节点异常时，内核精准唤醒 `Lead` 动态决定下一步（修 bug、打回、还是升级问人）；主屏自动投影只读进度图（`builtin:flow`），不用手工同步流程图。
- **刻意不选什么**：**刻意不在 `flow.json` 里引入 `if/else` 条件分支与循环语法**。凡是需要判断与权衡的分支都属于强模型的 `How`，交还给唤醒后的 Lead 动态改写 `flow.json`；编排引擎只保留确定性触发与状态投影，绝不滑向静态低代码流程图。

## P1-4：并行工作区的环境踩踏与现场易碎

- **痛点**：同一仓库并发跑 3~4 个任务时，共用目录互相覆盖；用普通 `git worktree` 遇到 Rust / .NET / 前端重型项目，每开一个新任务都要重编几分钟；`git rebase` 遇冲突卡死在半途；主服务升级或关掉网页，后台跑着的编译/测试终端直接断掉。
- **具体解法**：
  - 每条 Track 拥有独立隔离现场：按需选用 Git worktree、Jujutsu `jj`（冲突不卡死、一键操作回滚）、Linux `OverlayFS`（共享只读预热构建缓存，秒开隔离层，见 [Track OverlayFS](../track-overlayfs.md)）或远程 `SSH` 主机；
  - 终端抽离为独立守护进程（`perga-term-bridge`），主服务热升级或浏览器关闭不断连，人与 Agent 观察和操作同一块终端屏幕。
- **刻意不选什么**：**刻意不把执行环境搬进封闭云端容器**。真实研发与研究强依赖本地私有仓库、内网数据、特定硬件与已有 CLI 登录态，隔离必须长在用户自己的机器与 SSH 目标上。

## P2-5：重复规矩的固化 vs. 冷启动过重

- **痛点**：每次开新任务都要在 prompt 里重复叮嘱同一套纪律（测试命令、双模型 Review、指标表格式）很低效；但如果产品一开始就逼用户选重型模板、填一堆配置，或者模板需要手写几百行前端代码，用户十分钟就会流失。
- **具体解法**：
  - **默认零模板起步**：新建 Track 只需要说一句话，像聊天一样零摩擦开始；
  - **按需挂极轻协议**：等重复规律和红线浮现后，再按需挂载内置协议（当前三份标杆协议主文件均已压至 **27–40 行**）或让 Lead 现场生成/微调，打包账本字段、路由规则、测试门禁和内置只读视图，不用了随时可拆。
- **刻意不选什么**：**刻意不做重型模板前端框架，也不在业务数据里镜像维护执行流程**。所有任务进度与拓扑统一由内核 `builtin:flow` 投影，90% 的视图走原生内置组件（`builtin:flow` / `builtin:table` / `builtin:list`），仅在原生原语确实无法表达时才放行极简自定义图形组件，防止协议本身僵化变重。

## P3（刻意暂缓的下一步痛点）

在单条 Track 的上述 P0–P2 痛点彻底打磨顺滑之前，以下迈向“多任务智能组织”的更高阶痛点目前**刻意不做重设计**，只保留最轻的接口与诚实记录：

1. **多 Track 并行时的全局注意力过载**：目前只有 `Today` 每日变更流，尚未做 10+ 条活跃轨道并存时的全局待审批收件箱与噪音分级；
2. **跨 Track 的历史经验断裂**：目前只解决了单条 Track 内部不失忆，跨月、跨多个已关闭 Track 的决策归档与避坑复用尚未打通；
3. **多 Track 强耦合改同一模块的协同冲突**：目前跨 Track 仅靠异步 `Mail` 轻量唤醒，尚未解决强依赖多轨自动合并编排；
4. **前十分钟冷启动转化**：如何让首次上手的用户在第一个轻量任务里就立刻感受到比裸 CLI 更好用，而不是等到第三天才体会到长期价值。

## 与同类范式的差异

| 产品范式 / 代表 | 隐含前提 | 与 Perga 的本质差异 |
| :--- | :--- | :--- |
| 单厂 Coding Agent（Claude Code / Codex） | 强化单兵智力与单回合执行 | 强力单兵但绑定单一厂商；Perga 解的是跨厂混编、异构互审与跨天防漂移 |
| 并行 Worktree 管理台（Conductor / Emdash / Vibe Kanban） | 解决单机多开 CLI 的窗口与分支冲突 | 仍以多聊天框 + Diff 为中心；Perga 补齐只读活报告账本、审执制衡与 0-Token 编排唤醒 |
| 无人后台工厂（OpenAI Symphony / Gas Town） | 把代码工单变成高吞吐无头流水线 | 偏黑盒代码工厂；Perga 强调十秒可读的活报告、随时精细 Steer 与跨场景复用 |
| 静态工作流平台（Dify / 扣子 / n8n） | 模型智力不足，需要人画死执行步骤 | 易陷入过优化与僵化；Perga 默认无模板起跑，放开执行步骤，只锁账本与红线 |
| 虚拟公司框架（Paperclip） | 照搬人类公司静态职级组织 AI | 按固定岗位编织；Perga 按具体任务建 Track，先打穿单任务闭环再演进跨任务协同 |
