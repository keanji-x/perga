# 典型场景应用

基于 [产品设计与痛点优先级](design.md) 中按优先级落地的最小解法，仓库内提供了三份内置运行协议（位于 [templates/](../../templates)），在三个风格迥异但同样跨越数天至数周的真实场景中验证这套“小设计”够不够用、以及各自卡在哪。

## 场景落地对照

| 具体场景（内置协议） | 该场景最痛的具体问题 | 用到了哪些核心解法 | 当前真实局限 |
| :--- | :--- | :--- | :--- |
| 仓库持续交付（[`agents-delivery`](../../templates/agents-delivery)） | 多分支重编踩踏、单测绿但架构烂、口头 `AGENTS.md` 总走样 | 隔离缓存工作区 + `builtin:flow` 并行异构双 Review 与打回闭环 + 写任务必填全量测试 Gate + 0-Token `watch` PR CI + 合并前人工确认 | 单人多轨并行交付已顺滑；多轨强耦合改同一组文件时仍需人工协调合并 |
| 跨周 OKR 持续优化（[`okr-loop`](../../templates/okr-loop)） | 优化几天就忘掉旧实验、为刷表面数字偷偷删用例作弊 | 自动盖时间戳的四列 KR 总账（`builtin:table`）+ `builtin:flow` 每日 `cron` 采集刷榜 + 实验前置局部 Expect 核查 + 回归显式回滚与独立归因 | 已沉淀可追溯实验账本；跨周历史失败经验的自动复用仍待加强 |
| 个股长期投研（[`equity-research`](../../templates/equity-research)） | 研报聊完即散、反馈滞后数月、极易陷入确认偏误 | 无框价格区间轴 + 事件时间线（`builtin:list`）事前 Expect 与事后核查（`beat`/`inline`/`miss`）+ 常青论点与证伪红线 + `builtin:flow` 定期与异动异构复核 | 验证了非代码场景的通用性；当前依赖外部数据源配置，适合作为高深度个人研究样本 |

---

## 场景一：仓库维护与特性交付（`agents-delivery`）

这是目前打磨最深、闭环最完整的主场景，直接对准 P0–P1 四个最硬的工程痛点：

- **实际怎么用**：Lead 先对齐设计边界 → 在共享预热缓存的 OverlayFS / `jj` / SSH 隔离工作区派发实现 Worker → 实现完结后强制路由至异构只读模型做**并行双路独立 Review（Review A ∥ Review B）** → 有阻塞项自动打回修复 → 写任务必过全量测试 Gate → 提 PR 后挂 0-Token `watch(prChecks)` 盯 CI，主屏直接以原生 `builtin:flow` 投影真实交付拓扑，全绿后由人类在桌面或手机一键批复合并。
- **当前边界**：单人并行推进多条相对独立的复杂 PR 已经很顺手；多条 Track 强耦合修改同一核心模块时，跨轨合并编排仍需人工统筹。

## 场景二：跨周工程指标持续优化（`okr-loop`）

针对压低 CI 耗时、消除 Flaky Test、降内存占用这类容易烂尾的持续调优任务：

- **实际怎么用**：锁定稳定 `Objective` 与内核自动维护时间戳的四列 `KR` 总账（`builtin:table`）→ 通过 `builtin:flow` 挂载每日 `cron` 采集脚本刷新真实指标 → Lead 围绕缺口规划实验，前置写明可核查的局部 `Expect` → 隔离环境实测，达标合入，未达标或引起回归则显式回滚并由独立归因模型复盘。
- **当前边界**：把零散尝试沉淀成了可回溯的实验账本，有效遏制了指标作弊与遗忘；跨周历史失败经验的自动归因复用仍需继续补强。

## 场景三：个股与主题长期深度投研（`equity-research`）

验证同一套“活报告 + 小账本 + 异构复核 + 定时巡检”跳出代码领域后的实际手感：

- **实际怎么用**：以单一标的或主题为一条跨月 Track → 顶部无框价格区间轴直观呈现现价与估值锚点 → 下方事件时间线（`builtin:list`）追踪财报、产能与政策催化，严格对比事前 `Expect` 与落地核查（`beat / inline / miss`）→ 常青正文维护核心论点与证伪红线 → 通过 `builtin:flow` 每周定时刷新现价与同行估值，异动触发异构模型复核，模拟下单前经人工确认。
- **当前边界**：告别“聊完即散的一次性研报”，对抗确认偏误；目前强依赖外部行情与研究数据源插件，现阶段更适合作为高深度个人样本。

## 延展方式：先零门槛用起来，再按需沉淀

这三个场景只是内置样板，不要求任何新任务一上来就套模板。对于每周依赖安全审计、开源 Issue 分诊、持续竞品追踪等新需求，始终遵循 **P2 的克制原则**：先用一句自然语言开启普通 Track 跑起来，真正遇到重复痛点和红线时，再由 Lead 按需提炼成一份极轻的协议。
